# Vector RAG, chat and demo team — 2026-11-05

## Implemented flow

Knowledge text is split into overlapping excerpts (1,500 characters with 150-character overlap). A background worker creates real OpenAI `text-embedding-3-small` vectors with 1,536 dimensions. PostgreSQL stores them as native pgvector columns. Document indexing exposes PENDING, INDEXING, READY or FAILED; administrators can retry a failed index.

Retrieval embeds the question and executes cosine-distance ranking in PostgreSQL. Tenant, workspace, embedding-model, document-active and READY filters are applied to the query. The current small-workspace limits use exact vector search and a tenant/workspace B-tree scope index rather than a shared approximate-neighbor index. The five closest excerpts above a 0.25 similarity threshold are eligible. That threshold is a development heuristic, not a measured accuracy guarantee.

Both task generation and the new Chat section use this retrieval service. Chat answers must reference retrieved chunk IDs and exact supporting quotes. The server resolves source titles/document IDs and validates quotes before storing an answer; unsupported citations fail closed. No matching evidence produces an explicit insufficient-evidence response rather than an invented answer. A task uses document-only source metadata to avoid confusing a chunk ID with its document ID.

## Use the application

1. Open an organization and select Knowledge. Add approved text or use the clearly labeled demo operations handbook. Wait for its vector index to show READY.
2. Select Chat. Choose a workspace, open the seeded demo conversation or create a new chat, and ask a source-related question.
3. Queued/processing status is shown while the worker retrieves and generates. Expand Sources under a completed answer to inspect exact quotes.
4. Conversations persist and are restricted by the API to their creator within the active organization. A different member of the same organization cannot read another member's conversation. Source revocation immediately excludes retrieval and redacts affected stored answers on subsequent API reads; the UI polls history periodically.

Responses are generated server-side with the existing ignored backend OpenAI key and `store: false`. No provider key or raw vectors are returned to the browser. Prior questions provide conversational reference, not evidence. Chat has a serialized development cap of 20 accepted turns per organization per UTC day, one pending turn per conversation, bounded provider requests, worker leases/fencing and at most three claims. This is a development capacity policy, not invoice accounting or an availability commitment.

## Demo data

Each existing owned acceptance organization receives twelve labeled fictional profiles in the separate `demo_members` table, one fictional operations handbook and one queued demo conversation. Profiles use `example.invalid` addresses. They do not create Clerk accounts, users, actual memberships, invitations or permissions, and cannot sign in. Displayed demo roles are sample labels only. Existing real memberships and owner protections remain unchanged.

The local seeder is restricted to the two existing owned acceptance organizations and is idempotent:

```sh
uv run --locked --package orqentra-api python scripts/seed_workforce_demo.py --local
```

It uses restricted runtime transactions for writes after read-only local ownership discovery. It never creates a public authentication bypass or sends invitations/messages. The demo conversation's assistant response is generated by the real RAG worker; it is not a canned answer presented as live inference.
